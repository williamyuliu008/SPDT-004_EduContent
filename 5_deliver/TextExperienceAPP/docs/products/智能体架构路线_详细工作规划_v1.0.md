## 二、Phase 0: 架构定型 (7/18-7/20)

### 目标是定义标准，而不是写代码。这一阶段的所有产出会被 Phase 1-3 反复引用。

### 任务 0.1: 小龙虾统一API v1.0 正式规范

**产出**: `docs/specs/lobster-api-v1.yaml` (OpenAPI 3.0)

```
端点                      方法    用途                    7月形态       8月形态
──────────────────────────────────────────────────────────────────────────
/health                   GET     健康检查                返回mock      真实状态
/task                     POST    通用任务调度            规则引擎      LLM驱动
/task/{trace_id}          GET     异步任务结果查询        pending       真实结果
/knowledge/query          POST    知识库查询              JSON文件      RAG向量
/knowledge/import         POST    知识库批量导入          JSON验证      图谱更新
/content/import           POST    内容批量导入            格式验证      自动入库
/content/export           POST    APP内容导出到PC         数据转储      全局分析
/state/write-back         POST    APP状态写回PC           接收存储      触发分析
/state/query              POST    PC查询APP状态           存根值        跨APP关联
/app/register             POST    APP注册(声明task_type)  手动注册      自动发现
```

**关键决策：**
- `app_id` + `task_type` 构成路由键，小龙虾据此分发到不同的处理引擎
- `user_context` 可选但推荐——每个请求可以携带APP侧的用户画像快照
- 所有响应包含 `trace_id`，支持异步长任务（LLM生成可能需要秒级延迟）
- `/app/register` 端点：APP首次接入时声明自己支持哪些 task_type，小龙虾据此配置路由规则

### 任务 0.2: Agent Core 公共模块设计

**产出**: `common/agent-core/` 目录结构设计文档

```
common/agent-core/
├── AgentProfile.ets          # A维度: UserProfile CRUD
├── IntentContext.ets         # B维度: 当前上下文 + 操作序列
├── InputAssist.ets           # C维度: 意图预填 + 冷启动引导
├── OutputAction.ets          # D维度: D1-D4 分级操作 + 风险矩阵
├── ContentPipeline.ets       # E维度: JSON解析 + 题库/知识库管理
├── LobsterClient.ets         # G维度: 小龙虾HTTP客户端封装
├── EnvAwareness.ets          # H维度: 电池/通知/场景感知
├── UndoManager.ets           # I维度: 操作撤销(3分钟窗口)
└── AgentEngine.ets           # 编排层: 连接各维度 + 生命周期
```

**设计原则：**
- 每个维度是独立模块，不互相依赖（便于按需引入）
- `AgentEngine` 是唯一的编排入口，APP只需实例化它
- 所有模块基于接口（interface），便于测试和 mock
- 零 LLM 依赖——Phase 0-2 全部用规则引擎 + 本地存储

### 任务 0.3: 数据模型标准化

**产出**: `docs/specs/data-models-v1.md`

定义跨维度、跨APP的标准化数据结构：

```typescript
// UserProfile (A维度核心)
interface UserProfile {
  learning_style: 'visual' | 'auditory' | 'kinesthetic'
  target_score: number
  patience_level: number  // 1-5
  error_attribution: {
    conceptual: number    // 概念性错误占比
    calculative: number   // 计算性错误占比
    time_pressure: number // 时间压力错误占比
  }
  strengths: string[]
  weaknesses: string[]
  updated_at: string      // ISO 8601
}

// IntentContext (B维度核心)
interface IntentContext {
  current_tab: string
  current_view: string
  recent_actions: ActionRecord[]  // 最近N个操作
  session_start: string
  cross_session_bookmark?: string // 跨会话恢复标记
}

// TaskRequest (G维度核心 — 小龙虾请求)
interface TaskRequest {
  app_id: string
  task_type: string
  payload: Record<string, any>
  user_context?: UserProfile
  intent?: IntentContext
}

// TaskResponse (G维度核心 — 小龙虾响应)
interface TaskResponse {
  status: 'ok' | 'error' | 'pending'
  result?: Record<string, any>
  error?: { code: string; message: string }
  trace_id: string
  estimated_ms?: number  // 异步任务预计耗时
}
```

## 七、架构决策记录 (ADR)

### ADR-001: APP不做LLM调用，只做消费

**决策：** 所有LLM调用由小龙虾统一发起，APP只通过 HTTP API 消费结果。
**理由：** ①避免每个APP各自管理API Key ②统一成本模型和降级策略 ③跨APP数据关联只有小龙虾能做到。
**影响：** APP始终可以在无LLM环境下运行（通过规则引擎 fallback）。

### ADR-002: 8维模块独立，AgentEngine编排

**决策：** 每个维度是独立 ArkTS 模块，AgentEngine 负责生命周期和依赖注入。
**理由：** ①不同APP需要的维度组合不同 ②独立测试 ③渐进式引入。
**影响：** 公共模块 `common/agent-core/` 的每个文件可以独立被引用。

### ADR-003: Phase 0-2 零LLM

**决策：** 所有智能体行为在 Phase 0-2 用规则引擎+本地数据驱动。
**理由：** ①验证架构不依赖LLM ②确保降级路径原生可用 ③减少对外部API的依赖风险。
**影响：** 即使小龙虾后端永久不接LLM，APP仍然有完整的智能体能力。

### ADR-004: 小龙虾API先mock后真实

**决策：** Phase 1 使用 Python/Flask mock 服务器验证协议，Phase 2+ 逐步替换为真实后端。
**理由：** ①APP侧开发不阻塞于后端 ②协议先行，验证接口设计 ③mock数据就是测试用例。
**影响：** Phase 1 的 LobsterClient 必须支持 configurable base URL。
