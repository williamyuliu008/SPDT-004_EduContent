## 一、智能体全景分类

根据 APP 功能特性，智能体分为五大类，每类对应鸿蒙 APP 的特定场景：

| # | 类型 | 核心能力 | 系统要求 | 鸿蒙 APP 示例 |
|:---|:---|:---|:---|:---|
| 1 | **操作执行智能体** | 读写 APP 内数据，按自然语言指令修改配置/内容 | 权限映射 + 操作日志 + 回滚 | coach（学习计划调整）/ zknote（笔记整理）/ rhyhtm-habit（习惯配置） |
| 2 | **问答助手智能体** | RAG 知识库问答，基于 APP 私有知识回答用户问题 | 数据封装 + 跨页上下文 | gaokao-agent（高考知识问答）/ harmonycoder（ArkTS API 问答） |
| 3 | **流程自动化智能体** | 提示→生成代码→反馈修正闭环 | 执行队列 + 异步处理 | harmonycoder（代码生成+审查+修正）/ quiz（出题+批改+解析） |
| 4 | **知识管理智能体** | 自动组织散落笔记/文档→构建知识图谱→发现知识盲区 | 知识图谱 + 个性化引擎 | coach（知识全景）/ mindmap（自动组织）/ flashcard（SM-2 复习链路） |
| 5 | **个性化学习智能体** | 追踪学习历史→定位薄弱环节→定制复习计划→模拟教师讲解 | 行为记录 + 教学模型 | coach（个性化学习）/ flashcard（自适应复习）/ gaokao-agent（六科诊断） |

## 二、四层架构模型

```
┌─────────────────────────────────────────────────────┐
│  L1 前端交互层                                        │
│  · 智能体入口按钮（页角/顶部/浮动）                      │
│  · 对话弹窗 · 差异对比 · 确认对话框                      │
│  · 视觉反馈（思考动画/进度条/结果高亮）                   │
├─────────────────────────────────────────────────────┤
│  L2 智能体中台层 ★核心★                                │
│  · 数据捕获模块    · 权限校验模块                        │
│  · 执行队列模块    · 审计日志模块                        │
│  · 对话状态管理    · 跨页上下文                          │
├─────────────────────────────────────────────────────┤
│  L3 业务逻辑层                                         │
│  · 各 APP 核心功能（不变）                              │
│  · 通过统一数据协议对接中台                              │
├─────────────────────────────────────────────────────┤
│  L4 数据存储层                                         │
│  · Preferences (本地 KV) / SQLite / JSON 文件           │
│  · AI 压缩存储（小模型提炼→压缩→存值）                   │
└─────────────────────────────────────────────────────┘
```

**核心设计法则：** 智能体中台是"能力枢纽"，业务层只关注功能逻辑，所有 Agent 交互通过中台对接。新 APP 开发时，中台层可作为模板嵌入。

## 三、五大通用模块

### 3.1 数据捕获模块

**职责：** 自动提取当前页面核心业务数据，过滤无关 UI 元素。

```
输入: 当前页面 @State 变量 + 用户操作历史
处理: 过滤 → 结构化 → 标注类型
输出: { pageType: "笔记详情", entities: [...], context: {...} }
```

**SPDT-001 实现：** `app.config.ts` 中声明各页面的数据抓取规则，运行时自动注入。

### 3.2 权限校验模块

**职责：** 确定 Agent 对每个数据实体的读/写/执边界。

```typescript
interface PermissionMap {
  entityName: string;      // 实体名
  currentValue: any;       // 当前值
  accessLevel: "read" | "suggest" | "modify";  // 读/建议/修改
  constraints?: string[];  // 修改约束（如"数值范围 1-100"）
}
```

**关键规则：**
- 默认 `read`，不可越级
- 危险操作（删除/批量修改）必须 `suggest` 级别（用户确认后执行）
- 约束条件在前端做第一道拦截，后端做第二道

### 3.3 执行队列模块

**职责：** 管理 Agent 的操作请求，支持延迟执行→用户确认→批量提交→回滚。

```
用户确认前: 操作指令暂存队列，展示预览
用户确认后: 批量执行 → 审计记录 → 结果反馈
用户拒绝后: 清空队列并丢弃
执行异常后: 自动回滚 → 通知用户 → 记录错误
```

**关键设计：** 区分"预执行"和"正式提交"两个阶段。预执行在内存中模拟，不落盘；正式提交后才写存储。

### 3.4 审计日志模块

**职责：** 记录 Agent 的所有读写操作，确保可追溯。

```
日志结构:
├── 操作时间
├── 操作人（哪个 Agent）
├── 操作类型（读/写/删）
├── 修改前值 vs 修改后值（diff）
├── 会话 ID
└── 回滚信息
```

**审计级别：**
- 读操作 → 低日志（仅统计）
- 写操作 → 完整日志（含 diff）
- 删除操作 → 完整日志 + 30 天保留期

### 3.5 对话状态管理

**职责：** 维护 Agent 与用户的对话上下文，支持跨页面追问。

```
会话结构:
├── sessionId
├── 对话历史（最近 N 轮）
├── 当前页面上下文（自动注入）
├── 跨页引用（用户提到"刚才那张卡片"）
└── 中间变量（Agent 推理的临时数据）
```

## 四、统一数据协议

所有 APP 的智能体中台通过统一的 JSON 协议与业务层对接：

```json
{
  "protocol_version": "1.0",
  "page": {
    "type": "flashcard_review",
    "entity": "card",
    "currentValue": { "front": "SM-2 算法", "back": "间隔重复算法的核心是..." },
    "accessLevel": "modify",
    "constraints": ["back 字段不超过 500 字"]
  },
  "user": {
    "history": ["该卡片已复习 3 次", "上次正确率 80%"],
    "preferences": { "voiceInput": true }
  },
  "agent": {
    "type": "操作执行",
    "action": "modify",
    "instruction": "把卡片背面的解释改得更简洁"
  }
}
```

**协议核心三要素：实体名 → 当前值 → 操作许可。** 无论哪种 Agent 类型，都遵循此协议访问 APP 数据。

## 五、UI/UX 设计规范（智能体交互）

### 5.1 入口设计

| 场景 | 推荐方案 | 反例 |
|:---|:---|:---|
| 全页级 Agent | 页面右下角固定浮动按钮 | 藏在二级菜单中 |
| 局部级 Agent | 选中内容后弹出浮动工具栏 | 每次都要切到对话页 |
| 全局级 Agent | 底部导航栏独立入口 | 藏在设置里 |

### 5.2 反馈设计

**三层反馈机制：**

| 时机 | 展示内容 | 设计要点 |
|:---|:---|:---|
| Agent 执行前 | "已获取当前页面数据" → 展示上下文预览 | 让用户知道 Agent 理解了当前页面 |
| Agent 执行中 | 思考动画 / 进度条 / 步骤提示 | 别让用户对着空白等待 |
| Agent 执行后 | 修改对比（diff）/ 结果高亮 / 成功提示 | 清晰展示改了什么 |

### 5.3 确认设计

```
危险操作（删除/批量修改）:
  → 必须弹窗确认 + 展示前后对比

普通操作（修改单个字段）:
  → 可选轻量确认（toast + 撤销按钮）

只读操作（问答）:
  → 无需确认，直接展示结果
```

### 5.4 品牌适配

| 品牌 | 组件配色 | Agent 浮标风格 | 对话气泡 |
|:---|:---|:---|:---|
| ThinkKit #5B8C5A | 森绿主色 + 浅绿底色 | 知识感·圆角·半透明 | 卡片式·左对齐 |
| Craftsman #E87A2A | 工匠橙·深色模式优先 | 工具感·直角·不透明 | 紧凑型·代码块样式 |
| HarmonyCoder #7B2D8E | 紫·暗色 IDE 风 | 代码感·inline | 三段式·代码/解释/操作 |
| RhythmHabit #3B82B0 | 蓝·圆润·温暖 | 治愈感·微动画 | 圆角·图标化 |
| GaokaoAgent #C44536 | 红·学院风 | 庄重·最小干扰 | 结构化·分段 |

### 5.5 评估维度

| 维度 | 衡量方法 | 目标 |
|:---|:---|:---|
| 任务完成率 | 用户发出指令→Agent 正确执行的比率 | > 90% |
| 视觉干扰度 | 添加 Agent 入口后，页面其他元素的点击率下降比例 | < 5% |
| 情感满意度 | 退出 Agent 功能时弹"这个功能有帮助吗？" | > 80% 好评 |

## 六、安全与合规

### 6.1 数据边界

- Agent 的读/写边界必须在 `app.config.ts` 中显式声明
- 禁止 Agent 访问系统级数据（联系人/相册/文件系统，除非用户明确授权）
- AI 模型调用优先本地处理，敏感数据不上传云端

### 6.2 模型选择

| 场景 | 推荐方案 | 原因 |
|:---|:---|:---|
| 简单分类/排序 | 本地规则引擎 | 低延迟，无隐私风险 |
| 中等复杂度 NLP | 本地小模型 / 离线模型 | 离线可用，数据不出设备 |
| 复杂推理/生成 | 云端大模型（需用户确认） | 能力上限高，但需隐私提示 |

### 6.3 人工审核点

以下场景必须有人工确认环节：
- 删除用户数据
- 修改付费设置
- 向外发送数据
- 修改学习计划的核心参数

## 八、附录：设计清单

新 APP 立项时，按此清单检验智能体设计：

- [ ] Agent 类型确定（操作执行/问答/流程/知识/学习 → 单选或多选）
- [ ] 数据协议定义（实体名 → 当前值 → 修改许可 的映射表）
- [ ] 权限边界声明（哪些数据只读？哪些可修改？）
- [ ] 入口位置设计（浮动按钮/底部栏/选中弹出 → 在 UI 稿中标出）
- [ ] 三类反馈设计（执行前/中/后的视觉反馈方案）
- [ ] 确认流程设计（哪些操作需用户确认？确认界面的前后对比格式）
- [ ] 审计日志方案（操作记录的存储格式和查询接口）
- [ ] 品牌适配（Agent 组件颜色/圆角/字体/图标与品牌色一致）
- [ ] 评估计划（上线后用什么指标衡量 Agent 的效果）
