## 〇、产品定位

一款**面向高考文科（史地政）的 AI 驱动知识卡片 APP**，鸿蒙 NEXT 平台。

核心设计哲学：「剧本式学习」——用逻辑链串联孤立知识点，节点卡用于抽查记忆，AI 辅助制卡与答疑。

| 维度 | Anki | 考点卡片APP |
|:---|:---|:---|
| 数据模型 | 牌组 → 笔记 → 卡片 | **学科 → 模块 → 链（剧本）→ 节点卡** |
| 管理复杂度 | 高（21种笔记类型、过滤牌组） | **低（3级目录 + 生熟标记）** |
| 复习机制 | SRS 算法驱动 | SRS（知识卡）+ 周期精练（能力卡）+ **链级复盘** |
| AI 能力 | 无内置 AI | **制卡、答疑、出题、链生成** |
| 内容组织 | 牌组/标签 | **链叙事 + 双向链接 + 脉络浏览** |
| 连接感 | 弱（翻卡不呈现前后文） | **强（翻任意卡一键看所在整条因果链）** |

## 一、核心数据模型

### 1.1 双轨制

```
学科
 └─ 模块（如：中国近现代史）
     └─ 链/剧本（Chain）── 1对多 ──→ 节点卡（Card）
                                    ├─ 知识卡（SRS驱动）
                                    ├─ 能力卡（周期精练）
                                    └─ 特殊卡（文明底色/场景判断/差异/批判）
```

### 1.2 Chain（逻辑链 / 剧本）

| 字段 | 类型 | 说明 |
|:---|:---|:---|
| `chain_id` | text | 唯一ID，如 `HIS_LATE_QING_01` |
| `title` | text | 链标题，如「鸦片战争：危机—反应链」 |
| `subject` | enum | 历史 / 地理 / 政治 |
| `module` | text | 所属模块 |
| `chain_type` | enum | 因果链 / 时序链 / 对比链 / 要素链 / 理论运用链 |
| `narrative` | rich text | 四段式叙事（逻辑主线/时空舞台/关键人事/去向今启） |
| `child_cards` | array | 关联节点卡ID列表 |
| `related_chains` | array | 关联链ID列表 |
| `tags` | array | 标签 |
| `last_review` | date | 上次整链复盘日期 |
| `review_interval` | int | 链级复盘间隔（天） |

### 1.3 Card（节点卡）— 极简

| 字段 | 类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| `card_id` | text | ✅ | 唯一ID |
| `chain_id` | text | ✅ | 所属链 |
| `chain_role` | enum | ✅ | 背景条件/触发事件/中间过程/结果/反例/规律 |
| `front` | rich text | ✅ | 设问 |
| `back_core` | rich text | ✅ | 核心答案（1-2行，踩分词级别） |
| `maturity` | enum | ✅ | 🔴未熟 / 🟡模糊 / 🟢熟 |
| `card_type` | enum | ✅ | knowledge / competency / scenario / civilization / critical |
| `note` | text | ❌ | 简短备注 |

**明确不做**：难度星级、错误计数、复习时间等冗余元数据。这些信息放在链的叙事中，不膨胀卡片字段。

## 二、APP 功能模块

### 2.1 学习引擎

| 功能 | 说明 | 优先级 |
|:---|:---|:---|
| **脉络阅读** | 按链逐段叙事呈现，支持"阅读态"和"抽卡态"切换 | P0 |
| **节点抽查** | 基于生熟标记的 SRS 抽查，🔴🟡优先，🟢低频 | P0 |
| **生熟标记交互** | 翻卡后三态按钮：不熟/模糊/熟了 | P0 |
| **"看剧本"按钮** | 翻任意节点卡时，底部一键展开所在因果链 | P1 |
| **链级复盘提醒** | 按链设定复盘周期，到期提醒通读整条链 | P1 |
| **场景判断训练** | 能力型卡片不以"记住背面"为目标，而是思路对照 | P2 |

### 2.2 AI 能力（核心差异化）

这是本项目与 Anki 最根本的区别。

#### 2.2.1 AI 问答（基于卡片/链上下文）

```
用户操作流程：
1. 翻到某张卡片或阅读某条链
2. 呼出 AI 面板（浮动按钮 / 侧边栏）
3. 提问：与当前卡片/链内容相关的问题
4. AI 自动带入当前上下文（卡片 + 所在链的完整叙事文本）
5. AI 回答，对话历史保存
```

**场景示例**：
- 翻到「鸦片战争直接原因」卡 → 问"虎门销烟为什么是这个时间点发生？之前有没有禁烟？"
- 阅读「晚清危机链」→ 问"如果林则徐没被罢免，局面会不同吗？"
- 翻到「矛盾分析法」卡 → 问"能举个我生活中判断敌我矛盾和内部矛盾的例子吗？"

#### 2.2.2 AI 辅助制卡

| 子功能 | 输入 | 输出 | 优先级 |
|:---|:---|:---|:---|
| **文本转卡片** | 用户粘贴/输入一段文本 | AI 提取关键点 → 生成 front/back 建议 → 用户确认/编辑 → 保存 | P0 |
| **OCR 转卡片** | 拍照识别教材/笔记 | OCR → AI 提取 → 生成卡片建议 | P1 |
| **AI 写链** | 用户指定知识点范围 | AI 生成链的四段式叙事文本 → 标注关键记忆点 → 自动生成节点卡 | P1 |
| **链→卡批量生成** | 已有链的叙事文本 | AI 或规则引擎从叙事中提取关键记忆点 → 生成节点卡 | P0 |

#### 2.2.3 AI 回答转卡片

```
用户操作流程：
1. 呼出 AI 面板，提问
2. AI 给出回答
3. 用户觉得回答内容有价值 → 点击"转卡片"
4. AI 自动从回答中提取关键知识点
5. 生成 front/back 建议 + 自动匹配所属链
6. 用户确认/编辑 → 保存为节点卡
```

#### 2.2.4 AI 模拟出题

| 子功能 | 说明 | 优先级 |
|:---|:---|:---|
| **基于链出题** | 选择一条链 → AI 生成不同难度的模拟题 | P2 |
| **难度分级** | Ⅰ直问直答 / Ⅱ单材料综合 / Ⅲ跨章节开放 | P2 |
| **出题视角** | 从答题者→命题者，反向训练 | P2 |

#### 2.2.5 AI 交互设计要点

| 设计点 | 方案 |
|:---|:---|
| 呼出方式 | 右下角浮动 AI 按钮，点击弹出半屏面板（类似微信小程序） |
| 上下文注入 | 当前卡片/链内容自动作为 system prompt 上下文 |
| 对话持久化 | 每条链/卡片关联的对话历史保存，下次打开可继续 |
| 流式输出 | AI 回答流式渲染，非阻塞等待 |
| API 层 | 抽象 AI 接口，支持切换后端（智谱 GLM / 本地模型等） |
| 离线降级 | 无网络时 AI 功能灰色不可用，本地学习功能不受影响 |

### 2.3 内容管理

| 功能 | 说明 | 优先级 |
|:---|:---|:---|
| **学科浏览** | 学科 → 模块 → 链 三级目录树 | P0 |
| **链创建/编辑** | Markdown 编辑器，四段式模板 | P0 |
| **卡片创建/编辑** | 极简表单（front/back/maturity/chain_id） | P0 |
| **批量导入** | 导入 Markdown/JSON/CSV 格式的链和卡片数据 | P1 |
| **搜索** | 全文搜索链标题+叙事+卡片内容 | P1 |
| **标签筛选** | 按标签筛选链和卡片 | P2 |

### 2.4 数据面板

| 功能 | 说明 | 优先级 |
|:---|:---|:---|
| **学习仪表盘** | 今日待复习数、总卡片数、熟练掌握率、连续天数 | P1 |
| **链级统计** | 每条链的卡片生熟分布、上次复盘时间 | P1 |
| **导出** | 导出为 Anki .apkg / CSV / Markdown | P2 |

## 三、简化 vs Anki 的管理设计

### Anki 中保留的

- SM-2 / FSRS 间隔重复算法
- 卡片翻转交互
- 本地优先存储
- 富媒体支持（图片、公式、音频）

### Anki 中简化的

| Anki 概念 | 考点卡片APP |
|:---|:---|
| 牌组 + 子牌组（可嵌套） | 学科 → 模块 → 链（最多3层） |
| 笔记类型（21种内置+自定义） | 仅5种卡片类型，字段统一 |
| 过滤牌组（复杂条件） | 标签筛选（简单） |
| 学习选项（步进、毕业间隔等） | 默认策略，不可调（或极简调节） |
| 卡片浏览器 | 链浏览 + 卡片列表 |
| 统计详情（30+图表） | 仅仪表盘核心指标 |
| 插件系统 | 无插件，AI 替代插件生态 |

### 新增的（Anki 没有的）

- **链/剧本数据模型**：知识的上下文和逻辑脉络是一等公民
- **脉络浏览**：翻卡时能看到所在因果链
- **AI 集成**：制卡、答疑、出题全部内置
- **链级复盘**：不只是卡片抽查，还有整链通读
- **场景判断训练**：能力型卡片有独立的交互逻辑

## 四、关键交互流程

### 4.1 日常学习流

```
打开APP → 仪表盘（显示今日待复习数）
  → 点击"开始复习"
  → 默认进入「链阅读模式」：按顺序阅读一条链的叙事
    → 阅读完一段 → 系统抽取该段关联的节点卡（优先🔴🟡）
    → 翻卡 → 标记生熟 → 继续下一段
  → 整条链读完 → 标记链复盘完成 → 下一链或结束
```

### 4.2 制卡流

```
方式A（手动）：
  链编辑页 → 新增节点卡 → 填 front/back → 选 chain_role → 保存

方式B（AI辅助）：
  AI面板 → 粘贴文本/拍照OCR → "生成卡片" → AI返回卡片建议
  → 用户编辑确认 → 选择所属链 → 保存

方式C（AI回答转卡片）：
  AI面板 → 提问 → 得到回答 → "转卡片"
  → AI提取关键点 → 生成front/back → 用户确认 → 保存
```

### 4.3 AI 问答流

```
当前页面（链阅读/卡片翻看） → 点击AI按钮
  → 半屏面板弹出，当前上下文自动注入
  → 用户输入问题
  → AI 流式回复
  → 对话保留在侧边栏历史中
  → 可从回答中一键转卡片
```

## 五、技术架构建议

### 5.1 平台与框架

- **平台**：HarmonyOS NEXT（API 14+）
- **UI 框架**：ArkUI + ArkTS
- **存储**：关系型数据库（RDB/RelationalStore）用于卡片元数据，文件系统用于链的叙事文本
- **SRS 引擎**：本地实现的 SM-2 / FSRS 算法（已有 thinkkit-flashcard 的 sm2.ts 可用）

### 5.2 AI 集成架构

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│  ArkUI 层   │────▶│  AI Service  │────▶│  LLM API    │
│  (AI面板)   │◀────│  (抽象层)    │◀────│  (智谱GLM等)│
└─────────────┘     └──────────────┘     └─────────────┘
       │                    │
       ▼                    ▼
┌─────────────┐     ┌──────────────┐
│  Card/Chain │     │  Prompt      │
│  Context    │     │  Templates   │
└─────────────┘     └──────────────┘
```

**关键设计点**：
- AI Service 为抽象层，支持替换后端
- Prompt 模板化：每种 AI 功能（答疑/制卡/出题/链生成）有独立模板
- 上下文注入：自动将当前卡片内容+所在链叙事拼接为 system prompt
- 流式渲染：支持 SSE 流式输出
- 速率限制 + 缓存：避免重复请求

## 六、待讨论 / 待决策

### 6.1 AI 相关
1. **AI 后端选型**：智谱 GLM（已有 AutoGLM 基础设施）还是其他？是否需要支持多后端切换？
2. **AI 成本控制**：是否需要本地模型（端侧推理）作为离线降级方案？鸿蒙端侧 AI 能力（MindSpore Lite）可行性？
3. **Prompt 工程**：制卡/出题/链生成的 prompt 是否需要针对史地政三科分别优化？
4. **上下文长度**：链的叙事文本可能较长（300-600字），拼接后 prompt token 消耗评估？

### 6.2 产品相关
5. **APP 命名**：现有 ThinkKit 品牌有 thinkkit-flashcard/flashcard2，新 APP 叫 thinkkit-examcard？还是独立品牌名？
6. **初始内容**：是否预装历史50链作为示例数据？预装内容的数据格式（Markdown → 链+卡的结构化数据）？
7. **SRS 算法选型**：SM-2 vs FSRS？FSRS 对文科记忆的适配性？
8. **多学科扩展**：首版只做史地政三科，后续是否开放自定义学科？
9. **场景判断卡的交互**：这类卡片没有"对/错"，如何设计 evaluation UI？是通过自评还是 AI 对比？

### 6.3 技术相关
10. **本地存储方案**：RDB（关系型数据库）对链的叙事长文本是否合适？是否需要文件系统 + 数据库混合方案？
11. **数据迁移**：从 Anki .apkg 导入的可行性评估？
12. **鸿蒙端侧 AI**：是否需要评估 HarmonyOS 的端侧推理能力（如意图框架、语音识别）？
