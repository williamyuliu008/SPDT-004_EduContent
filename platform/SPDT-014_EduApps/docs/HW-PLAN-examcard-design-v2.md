### 核心设计原则

1. **APP是容器，不是内容生产工具**：内容由 SPDT-004 管线生产，APP 负责导入/浏览/复习/AI增强
2. **剧本先行，卡片为注脚**：用户先读链的叙事文本（理解），再抽查节点卡（记忆）
3. **极简管理**：不做 SRS 自动调度、不做复杂元数据、不做提醒
4. **AI 内置但不臃肿**：答疑、制卡、出题三项核心能力

## 二、Token 消耗评估（问题 #6）

### 2.1 上下文注入方案

| 策略 | 注入内容 | 预估 Token | 适用场景 |
|:---|:---|:---|:---|
| **轻量（默认）** | 当前卡片 front + back + chain 标题 | ~150-250 | 快速卡片答疑 |
| **标准** | 当前卡片 + chain 叙事全文 + 同链其他卡 front 列表 | ~600-1200 | AI 制卡、转卡片 |
| **完整** | 当前卡片 + chain 叙事 + 同链全部卡片 + 关联链摘要 | ~2000-4000 | AI 写链、模拟出题 |

### 2.2 基于 PT-038 实际数据评估

以历史 v3 为例（129卡/16链）：

| 维度 | 实际数据 | Token 估算 |
|:---|:---|:---|
| 单卡 front+back_core | ~30-60 中文字符 | ~40-90 tokens |
| 单链叙事文本（meta.json 摘要） | ~100-200 中文字符 | ~150-300 tokens |
| 单条链下平均卡片数 | ~8张/链 | 合并上下文 ~500-800 tokens |
| 四幕微剧本完整文本 | ~800-1200 中文字符 | ~1200-1800 tokens |
| System Prompt（引导指令） | ~200-300 tokens | ~200-300 tokens |

**最坏情况（完整上下文 + 3轮对话）**：~4000-5000 tokens

**结论**：在主流 LLM（智谱 GLM-4 128K / GPT-4o 128K / Claude 200K）的可控范围内。**推荐的默认策略是「标准」上下文注入**（单个 chain 叙事 + 当前卡上下文），约 600-1200 tokens/次查询。对于 AI 写链等高消耗场景，使用「完整」策略。

### 2.3 上下文策略实现

```typescript
// AIService 上下文分级
enum ContextLevel {
  LIGHT,    // 当前卡片 front+back+chain_title
  STANDARD, // + chain 叙事全文 + 同链卡片 front 列表
  FULL      // + 同链全部卡片详情 + 关联链摘要
}

// 按 AI 功能自动选择级别
const contextMap = {
  'qa': ContextLevel.STANDARD,        // 答疑：需要完整上下文
  'card_gen': ContextLevel.STANDARD,  // 制卡：需要链的叙事
  'answer_to_card': ContextLevel.STANDARD,
  'chain_gen': ContextLevel.FULL,     // 写链：需要最大上下文
  'exam_gen': ContextLevel.FULL,      // 出题：需要完整知识链
};
```

### 2.4 多轮对话管理

- 保留最近 **5 轮**对话作为上下文（约 1500-2500 tokens）
- 用户可手动清除对话历史
- 切换卡片/链时自动重新注入新上下文

## 三、数据模型（简化版）

### 3.1 对齐 PT-038 卡片格式

PT-038 产出的卡片 JSON 格式：

```json
{
  "card_id": "H_近代_01_001",
  "chain_id": "CHAIN_近代危机_01",
  "chain_title": "鸦片战争链",
  "card_type": "原因",
  "front": "鸦片战争爆发的根本原因",
  "back_core": "英国工业革命后急需海外市场，中英贸易失衡",
  "back_detail": "关联知识链：鸦片战争链(CHAIN_近代危机_01) ...",
  "maturity": "??",
  "tags": ["#鸦片战争", "#原因"]
}
```

### 3.2 APP 内部模型（导入后）

| 字段 | 来源 | 说明 |
|:---|:---|:---|
| `card_id` | PT-038 原件 | 保持不变 |
| `chain_id` | PT-038 原件 | 关联链 |
| `chain_title` | PT-038 原件 | 链标题，用于 UI 显示 |
| `card_type` | PT-038 原件 | 节点卡/心法卡/链卡 |
| `front` | PT-038 原件 | 设问 |
| `back_core` | PT-038 原件 | 核心答案 |
| `back_detail` | PT-038 原件 | 详细解释+记忆技巧 |
| `maturity` | 导入时置 `生` | **仅二态：生/熟** |
| `tags` | PT-038 原件 | 标签 |

**新增 APP 侧字段**：
| `is_new` | bool | 是否本周新导入，用于仪表盘"新卡"计数 |
| `last_marked` | date | 上次标记生/熟的时间 |

**不做**：
- ❌ SRS 调度字段（next_review/interval/ease_factor）
- ❌ 错误计数
- ❌ 难度星级
- ❌ 复习提醒

### 4.1 内容管理

| 功能 | 说明 | 优先级 |
|:---|:---|:---|

| **搜索** | 全文搜索卡片 front/back | P1 |

### 4.2 AI 能力

| 功能 | 说明 | 优先级 |
|:---|:---|:---|
| **AI 问答**（标准上下文） | 呼出 AI 面板，自动注入当前卡+链上下文，流式回答 | P0 |
| **AI 制卡**（标准上下文） | 粘贴文本 → AI 提取 → 生成卡片 → 挂到链下 | P1 |
| **AI 回答转卡片** | AI 回答 → "转卡片" → 提取关键点 → 保存 | P1 |
| **AI 链生成**（完整上下文） | 指定范围 → AI 生成链叙事 → 标注记忆点 | P2 |
| **AI 模拟出题**（完整上下文） | 基于链出题，难度 Ⅰ/Ⅱ/Ⅲ | P2 |

- ❌ 链级复盘提醒（决策 #8）
- ❌ SRS 自动调度（决策 #4）
- ❌ 学习仪表盘（简化为仅显示卡片总数+生熟比例）
- ❌ 卡片编辑器（内容不在 APP 侧生产）
- ❌ 场景判断卡片（暂缓，PT-038 产出的"心法卡"已覆盖核心能力训练）

## 五、与 PT-038 的交接协议

### 5.1 导入格式

APP 接受以下格式导入：

**格式 A：PT-038 卡片包 JSON（推荐）**
```json
{
  "version": "3.0",
  "series": "历史_v3",
  "total_chains": 16,
  "total_cards": 129,
  "node_cards": [...],
  "strategy_cards": [...],
  "chain_cards": [...]
}
```

**格式 B：PT-038 Anki CSV（兼容）**
```csv
card_id,chain_id,chain_title,card_type,front,back_core,back_detail,maturity,tags
```

**格式 C：链元数据 JSON（可选，用于链阅读器叙事文本）**
```json
{
  "chain_id": "CHAIN_近代危机_01",
  "chain_title": "鸦片战争链",
  "chain_type": "原因类",
  "narrative": "19世纪中期，英国完成工业革命...",
  "related_chains": ["CHAIN_近代危机_02"]
}
```

### 5.2 导入行为

- 按 `chain_id` 去重（相同 chain_id 的卡片合并到同一条链下）
- 同 `card_id` 的新导入覆盖旧版本
- 生熟标记在导入时设为"生"
- 支持增量导入（不覆盖已有的"熟"标记）
