# 管线接口设计原则 v0.1

> **定位**：为内容制造五阶段管线定义接口契约，支持全学科内容流动
> **范围**：1_ingest → 2_structure → 3_render → 4_adapt → 5_deliver
> **依据**：内容制造管线执行规范 v1.0 + 当前架构实践

---

## 一、当前核心矛盾

### 1.1 scene_v2 不是通用接口

`scene_v2_schema.json` 是为**教育 B1 深度历史叙事**设计的：

```
scene_v2 字段          设计来源
─────────────────────────────────────
analogy_block         书法史×历史学 类比教学
five_skandha          认知佛学五蕴理论的教学映射
emotion_trigger       书法审美情绪曲线
knowledge_type I/II   类比适用性分类（强类比/受限类比）
```

**问题**：当"三角函数"、"化学反应方程式"、"英语语法"进入管线时，这些字段完全失配。

### 1.2 管线的真实职责

管线各阶段不需要理解内容的内部语义，只需要：

| 阶段 | 真实职责 |
|:---|:---|
| 1_ingest | 接收任意学科素材 → 提取知识点元信息 |
| 2_structure | 按体裁模板组织内容 → 产出该学科对应的结构化格式 |
| 3_render | 只看 capability 声明 → 渲染多形态输出 |
| 4_adapt | 理解知识结构 → 做学习路径编排 |
| 5_deliver | 打包 + 人类终检 → 分发 |

**结论**：接口设计应让管线在"不深度理解内容语义"的前提下完成以上职责。

## 二、接口设计原则

### 原则 1：外层统一 + 内层自治

```
┌─────────────────────────────────────────────────────┐
│  OUTER INTERFACE（统一结构，所有学科共用）           │
│  - subject_domain   : 学科领域                       │
│  - content_type    : 内容形态（B1/B2/B3/B4）        │
│  - capabilities    : 能力声明（管线可读）            │
│  - knowledge_type  : 知识类型（管线级别分类）        │
│  - source_chain_id : 知识溯源链                      │
└─────────────────────────────────────────────────────┘
│
│  INNER CONTENT（学科自治，领域自解释）
│  ┌─────────────────────────────────────────┐
│  │ [书法史] scene_v2 格式                   │
│  │   {analogy_block, five_skandha, ...}    │
│  ├─────────────────────────────────────────┤
│  │ [数学]   math_v1 格式                    │
│  │   {definition, theorem, procedure, ...} │
│  ├─────────────────────────────────────────┤
│  │ [化学]   chem_v1 格式                   │
│  │   {reaction, element, principle, ...}   │
│  └─────────────────────────────────────────┘
```

**管线只认外层**。领域内部格式由各学科知识工程师自定，管线通过 capability 决定渲染策略。

### 原则 2：capability 替代结构化 Schema 作为管线交互语言

管线不需要知道"这是 `analogy_block`"，只需要知道：

```
capability: ["needs_analogy", "needs_visual", "needs_procedure_step"]
```

这样数学、化学、物理都声明自己的能力，管线渲染器统一处理：

| capability | 渲染器行为 |
|:---|:---|
| `needs_narrative` | 渲染叙事场景（音频/视频） |
| `needs_analogy` | 渲染类比块（图解+对照） |
| `needs_procedure` | 渲染步骤流（流程图/分步卡片） |
| `needs_visual` | 渲染图示/示意图（SVG/动画） |
| `needs_interactive` | 渲染交互组件（练习/测验） |

### 原则 3：知识类型管线级别分类（跨学科通用）

不是 I/II/III/IV（五蕴），而是管线和教学通用的三级分类：

```
KNOWLEDGE_TYPE（管线级别，所有学科共用）
─────────────────────────────────────────
K_FACT    事实性知识    → 需要记忆 + 溯源
K_CONCEPT 概念性知识    → 需要理解 + 举例 + 类比
K_PROCEDURE 过程性知识  → 需要步骤 + 变式练习
K_METACOG  元认知知识   → 需要反思 + 自我评估
```

每个学科在自己的 inner format 中可以细分（如数学的"定理"/"公理"/"推论"），但出管线的统一用 K_* 标注。

### 原则 4：变换规则随身携带，不做跨学科强制映射

管线每个阶段之间的传递对象包含 **transform_hints**（变换提示），而不是强制的目标 Schema：

```
{
  "outer": { "subject": "MATH", "content_type": "B2", "capabilities": ["needs_procedure"] },
  "inner": { /* math_v1 原始内容 */ },
  "transform_hints": {
    "from": "2_structure.math_v1",
    "to": "3_render.procedure_step_v1",
    "renderer_capability": "needs_procedure",
    "required_outputs": ["video", "card"]
  }
}
```

**变换规则不是跨学科映射**（数学"定理"≠历史"事件"），而是**同一学科内从结构化到渲染格式的变换**。

### 原则 5：学科域注册制（Domain Registry）

管线通过学科域注册表了解每个学科能提供什么、需要什么：

```yaml
# MODLIB/domain_registry/math.yaml
domain: MATH
subjects: ["三角函数", "代数", "几何", "微积分"]
inner_schema: "math_v1_schema.json"
capabilities_supported: ["needs_analogy", "needs_procedure", "needs_visual"]
pipeline_stages:
  1_ingest: "math_knowledge_extractor"
  2_structure: "math_scene_builder"       # 输出 math_v1
  3_render: "math_renderer"              # 读取 capabilities → 输出多形态
  4_adapt: "math_difficulty_scorer"
```

管线路由时查域注册表，决定用哪个 adapter，不做硬编码。

## 三、两层接口规范

### 3.1 外层接口（Outer Interface）

所有学科共用的管线契约，出现在每个阶段之间的传递对象中：

```json
{
  "pipeline_package": {
    "version": "1.0.0",

    "outer": {
      "subject_domain": "MATH",           // 学科域（来自学科注册表）
      "subject_detail": "三角函数",         // 细分子域
      "content_type": "B1_deep_content",  // SOP B1/B2/B3/B4
      "content_type_detail": "定理探究型",  // 学科内部分类

      "knowledge_types": ["K_CONCEPT", "K_PROCEDURE"],

      "capabilities": [
        "needs_analogy",    // 需要类比（如：三角函数 ↔ 圆周运动）
        "needs_visual",     // 需要可视化（如：单位圆动画）
        "needs_procedure"   // 需要步骤（如：解三角方程的标准流程）
      ],

      "source_chain_id": "math_trig_sin_basic",
      "content_spec_id": "MATH_GAOKAO_B1_三角函数",

      "trust_level": "D",
      "produced_by": "2_structure.math_scene_builder",
      "timestamp": "2026-07-30T00:00:00+08:00"
    },

    "transform_hints": {
      "from_stage": "2_structure",
      "to_stage": "3_render",
      "renderer_type": "capability_driven",
      "required_outputs": ["audio_narrative", "visual_animation", "practice_card"]
    },

    "inner": {
      // 学科自治内容，由领域 adapter 解释
      // 管线只读 outer，不解析 inner
    }
  }
}
```

## 五、阶段间接口契约

### 5.1 各阶段对接口的使用方式

```
阶段       读 outer   读 inner   写 outer   写 inner
──────────────────────────────────────────────────────
1_ingest   ✗          ✗          ✅         ✗（生成）
2_structure ✅         ✗          ✅         ✅（填充）
3_render   ✅         ✗          ✅（追加）  ✗
4_adapt    ✅         ✅（部分）  ✅（更新）  ✅（更新）
5_deliver  ✅         ✗          ✅（终检）  ✗
```

### 5.2 阶段间传递格式

```
1_ingest → 2_structure：
  outer: subject_domain, content_type, capabilities, source_chain_id
  inner: 原始知识点列表（各学科格式）

2_structure → 3_render：
  outer: subject_domain, capabilities（丰富化）, knowledge_types
  inner: 学科结构化内容（scene_v2 / math_v1 / chem_v1 ...）

3_render → 4_adapt：
  outer: 已完成的 render_outputs 标注（哪些形态已渲染）
  inner: 渲染产物引用（音频/视频/卡片路径）

4_adapt → 5_deliver：
  outer: adaptive_path, quality_score, learner_recommendations
  inner: 学习路径编排（学科内格式）
```

## 六、能力路由（Capability-Based Routing）

3_render 通过 capability 决定渲染策略，而不依赖 inner content 的格式：

```
                    ┌─ needs_narrative ──→ NarrativeRenderer
                    ├─ needs_visual ─────→ DiagramRenderer / AnimationRenderer
capabilities ──────├─ needs_procedure ──→ StepRenderer
                    ├─ needs_analogy ─────→ AnalogyRenderer
                    └─ needs_interactive → QuizRenderer
```

每个 renderer 是学科可插拔的：

```yaml
renderers:
  HIST_ART:
    needs_narrative: "TextExperience/narrative_renderer"
    needs_analogy:   "TextExperience/analogy_renderer"
    needs_emotion:   "TextExperience/emotion_renderer"

  MATH:
    needs_visual:     "MathRenderer/diagram_engine"
    needs_procedure:  "MathRenderer/step_flow_renderer"
    needs_analogy:    "MathRenderer/analogy_bridge"
    needs_interactive: "MathRenderer/interactive_solver"
```

## 七、关键设计决策

### 决策 1：管线不需要统一的知识表示

管线不需要知道"三角函数"和"颜真卿"有什么共同知识结构。统一的是**交互语言**（capability + knowledge_type），不是**内容表示**。

### 决策 2：capability 是管线与学科的"最小共识"

管线不需要知道 sin(θ) 的定义是什么，只需要知道：
- 这个知识点需要类比 → 调用 MathAnalogyRenderer
- 这个知识点需要步骤 → 调用 MathStepRenderer

### 决策 3：inner content 对管线透明

管线只保证 capability 声明与实际内容一致，不验证 inner content 的学科语义（由学科 adapter 负责）。

### 决策 4：学科 adapter 是双向的

```
2_structure 输出 math_v1
           ↓ adapter
3_render 接收 math_v1 → 转换为 capability 声明 → 触发 renderer
```

adapter 在两个方向都起作用：
- **正向**（结构化→渲染）：将 inner content 的特征映射为 capabilities
- **逆向**（渲染反馈→结构化）：将渲染效果反馈回知识结构
